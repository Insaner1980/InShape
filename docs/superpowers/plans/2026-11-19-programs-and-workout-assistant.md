# InShape programs, exercise guides and Finnish workout assistant

## Implementation plan for the personal Android app

Prepared 19 November 2026 from the working tree of `codex/inshape-ui-polish`. Revised 20 November 2026 for the owner's choice of on-device API key storage. The Android app is `com.emmah.inshape`. The implementation target for hands-on verification is the owner's Pixel 9 running Android 17.

**Goal.** Make an ordinary gym visit easy to record after a long break. The owner can open a familiar exercise, see their machine settings, log what they actually did in Finnish, listen to their own music and revisit how they felt. An ordinary unscheduled visit is a complete workflow. Choosing an eight-week program is optional.

**Delivery status.** This document and 19 converted WebP illustrations are the deliverables of the planning task. The checkboxes below describe future work. The live app, database, manifests and services have not been changed by this task. The API key already exists. Its value is unnecessary for development with fixtures and must stay outside this document.

**Architecture decision.** Keep the journal, programs, calculations, library, listening data and all final writes on the phone. The owner enters a personal OpenAI API key on the Pixel. InShape encrypts it on the device and authenticates requests directly to OpenAI. Use a model for interpreting Finnish, extracting material from images and optionally voicing a short answer. Pass bounded proposals and evidence between these parts. Android owns validation, review, timing and persistence.

**Design inputs.** The owner's ten-feature brief, the conversation about returning to a familiar gym, the supplied program JSON and companion Markdown, and the current app define the scope. Product defaults proposed in this plan include a one-program rotation and speech only on request unless exercise introductions are explicitly enabled. The owner chose direct OpenAI access for this personal installation. Live model access still needs verification.

## 1. The experience to build

| Where | What the owner can do | What happens |
|---|---|---|
| Today | Resume, record a free workout, or start the next program session | An active workout takes priority. With no chosen program, the existing routine suggestion stays available. No onboarding interview or API setup is required. |
| Library | Browse the three programs, preview a day, review exercise matches, choose a program | Show frequency, time range, rotation and the shorter version. Opening a preview leaves the personal library and history untouched. |
| Active exercise | Open the guide, see personal setup and last comparable result, type or tap the microphone | Keep set logging and music controls accessible. A short preview shows exactly which set, machine, fields and units will change. |
| Exercise detail | View the demonstration, own machine photos, settings, aliases and next-use reminders | An illustration is shared by program entries. The owner's photos and seat settings stay attached to their confirmed machine. |
| History and Progress | Ask a question about the selected exercise, session, week or date range | Findings show dates, counts and tappable journal entries. Before, after and next-day observations retain their original phase. |
| Music | Ask for a playlist, review and reorder real local tracks, then create or update it | Show duration, missing metadata and unmet preferences. Playback starts only on a separate play action. |
| Settings | Save, replace or remove the OpenAI API key, change voice and answer style, inspect saved memories and usage | The visible interface follows the app's current English copy. The assistant defaults to Finnish and understands mixed Finnish/English exercise names. |

**Example visit.** Open Today and choose a free workout. Select the gym's leg press. If its seat setting is saved, it appears immediately. Say `“Tällä laitteella penkki neloseen ensi kerrallakin.”` Review the equipment-setting change. After one set, say `“Neljäkymmentä kiloa, kaksitoista toistoa.”` Confirm the reviewed set, then finish the visit even if that was the only exercise. On the next visit, open the dated record behind “last time.” A before-workout observation can describe discomfort already present on arrival. A next-day entry can describe stiffness separately. Both are optional.

**Visual fit.** Use the existing monochrome theme tokens, row components, typography and disclosure patterns. Keep the primary workout action pinned and offer one contextual assistant entry. Place long imports and evidence lists on full review screens, using a sheet for a brief set confirmation. Reserve error color for errors and destructive actions. Use accessible labels and spacing, with no colored edge stripes, dot separators or decorative badges.

## 4. Storage and write contracts

Implement each extension with the first feature that needs it. Proposed type and field names below define the intended interfaces. Use the current migration number at execution time. Export a Room schema at each actual version boundary, register each migration in the builder that opens that database and in its test setup, and test a direct upgrade from the shipped v1 schema. Within an unreleased batch, one coherent migration per database is sufficient.

| Data | Proposed representation and invariants |
|---|---|
| Reviewed catalog and equipment links | Versioned bundled catalog, stable program/day/slot keys and a local `ProgramExerciseLink(catalogExerciseId, exerciseId)`. Multiple machines can implement the same movement. Require one selected machine per slot at start, with an explicit choice if several match. A new personal exercise gets its own existing-style exercise/equipment IDs. |
| Active program | Singleton `ProgramEnrollment` with an enrollment ID, catalog ID/version, baseline date, phase week and next day index. Persist the selected week with a manual hold/advance control. Initial week is 1. Display week guidance as editable context. A gap never escalates the phase automatically. At week 8, offer continue/repeat/switch. |
| Workout source | Nullable enrollment/program/version/day/short-day fields on the workout. Keep original slot key and planned exercise identity on its session item when substituting. Copy display title, actual exercise, equipment and basis through existing session snapshots. Keep old sessions readable after editing, switching or deleting library entries. |
| Targets and groups | Extend the planned set target to represent an inclusive rep range and per-side scope, keeping the legacy exact `reps` value readable. Add nullable planned rest seconds and group key/type/rounds as appropriate on routine/session snapshots. Retain duration targets in seconds. Store optional instructions and explicit numeric weight separately. Reject an inverted range, mixed incompatible units or a broken group before save. Preserve distinct per-round prescriptions if the source gives them. |
| Performed values | `SessionSet.load`, `reps` and `completedAt` remain authoritative for a completed set. Carry optional self-reported RIR and a per-side qualifier where entered. If sides differ, keep separate labeled results or ask for separate entries before save. Keep missing/zero distinct. Keep the existing optional pain/body check-in separate from RIR. Never fabricate RIR from “felt right.” |
| Memory | Reuse `Exercise.settings`, `nickname` and `notes` for the fields they own and session notes for session-only observations. Add a scoped persistent reminder/preference record for information without an owner today. Give it an ID, scope, target ID where needed, text, lifecycle and revision. A reminder for the next visit carries creation workout ID and can be acknowledged or dismissed explicitly. |
| Safe commands | Journal `AssistantReceipt(commandId, payloadDigest, targetId, resultIds)` and an equivalent receipt in the separate music database. Save the receipt and all covered writes in the same database transaction. One preview targets one database. Generate command IDs on device, retain them across rotation/process death and use stable existing entity IDs for targets. |
| Music | Add an optional per-track user label for energy/mood and `ListeningEvent(eventId, trackId, workoutId?, startedAt, playedMs)` in Music Room. Persist actual audible playback intervals with an event ID stable across retries. IDs from different trees or replacement files remain distinct. |
| Assistant drafts and settings | Keep pending text and review data under a feature-owned local draft namespace. Reuse editor-draft storage only with explicit filtering in backup/export. Keep raw voice recordings temporary and remove them on send/cancel/failure teardown. Keep the encrypted OpenAI API key in the app’s private no-backup directory. Section 6 defines how the Android Keystore key protects it. A restore invalidates pending previews before they can write. |

**Write sequence.** Build a proposal from a snapshot, resolve identifiers locally, show before/after and scope, validate edits, then confirm. Inside `withTransaction` look up an existing receipt first. On an identical digest return its stored result. Reject command-ID reuse with a different digest. Then re-read parent revision, current item, target row values and membership as applicable. Apply all changes using existing repository semantics. Write receipt, consume draft, commit and refresh. If content or identity changed, return a “Review again” result including the current values. Checking only a button's enabled state cannot protect against retried deliveries or manual edits while a response was in flight.

**Scope of a write.** The response model proposes fields and operation kinds. It has no database handle, navigation authority, background permissions or general-purpose action runner. Local selection lists issue short opaque handles scoped to one request. Resolve them against current records before presenting a preview. Treat source notes, signs, imported text and track titles as data. Model refusals, malformed schema results, unknown handles and unsupported unit conversions lead to clarification or a retained draft.

## 6. Provider contract, privacy, configuration and failure handling

### Direct OpenAI requests from Android

Use the fixed HTTPS origin `https://api.openai.com` for REST and the corresponding secure WebSocket origin for Realtime. Attach the owner's bearer credential only in the authorization header of these requests. Reject redirects on authenticated requests. Model output, imported links and equipment photos cannot select a destination. Only the operations below may use this client.

| Android operation | OpenAI destination and model | Input and output contract |
|---|---|---|
| Read key status | On device | Report whether a credential is stored and readable. This performs zero network calls. API validity and model access are established only by an explicit live request. |
| Interpret a request | `POST /v1/responses` with `gpt-5.4-mini` | Send the current Finnish request, action-specific schema, constrained candidate handles and the minimum necessary context. Set `store: false`. Return a validated intent, clarification or grounded explanation. |
| Extract an image or program | `POST /v1/responses`, same model with text/image inputs | Submit selected images as inline supported image input and/or pasted text. Require structured rows, source references, uncertainty and unresolved fields. Return bounded JSON. No remote file library. |
| Transcribe a clip | `POST /v1/audio/transcriptions` with `gpt-transcribe` | Multipart bounded recording. Supply Finnish language context and relevant exercise names as optional hints. Return a transcript for review. Keep numbers and negation visible for correction. |
| Read an approved answer aloud | `wss://api.openai.com/v1/realtime?model=gpt-realtime-2.1-mini` | Android opens one authenticated socket, submits short approved text and locale, requests one audio response and collects bounded `response.output_audio.delta` events. Check the final result, close the socket and play the negotiated audio format. Never start microphone capture or enable model tools for this operation. |

The text/vision model supports Responses, image input and structured outputs. Start with its documented pinned snapshot `gpt-5.4-mini-2026-03-17` where available. Keep the model IDs and endpoint paths in the Android gateway as non-secret constants. Verify availability with the owner's project during live acceptance. For strict structured responses use `text.format` with `type: "json_schema"`, `strict: true`, a root object, bounded alternatives and closed properties. Express optional values as nullable required properties where the schema requires it. Handle refusals and incomplete responses before decoding a domain result. [Model capabilities](https://developers.openai.com/api/docs/models/gpt-5.4-mini) and [Structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs)

The file-transcription guide recommends `gpt-transcribe` for a completed recording. The current speech-generation guidance directs new integrations to Realtime. The older dedicated speech models are scheduled for shutdown on 6 January 2027. For cloud narration, send text input with a single `response.create`, request audio output, handle errors/closure, and use the format negotiated by the session. Test pronunciation and any added or omitted words in Finnish. Route exact sets, units and equipment settings to deterministic local readback. [File transcription](https://developers.openai.com/api/docs/guides/speech-to-text), [speech model transition](https://developers.openai.com/api/docs/guides/text-to-speech), [Realtime conversations](https://developers.openai.com/api/docs/guides/realtime-conversations) and [Realtime WebSocket protocol](https://developers.openai.com/api/docs/guides/realtime-websocket)

**Credential storage on the Pixel.** Generate a device-local, non-exportable AES-256 key with `AndroidKeyStore`. Encrypt the entered OpenAI API key with `AES/GCM/NoPadding` and a fresh provider-generated IV for each save. Atomically store only the version, IV and authenticated ciphertext under `Context.noBackupFilesDir`. Read the credential only for the credential-status check or an owner-requested API operation. Keep the plaintext out of Room, saved UI state, APK resources, logs, backups and exports. Clear the input field after saving. The Keystore protects the encryption key. The API credential is briefly available to the running app when authenticating a request. This is the owner's explicit choice for a personal installation. OpenAI advises against storing API credentials in mobile clients. [Android Keystore](https://developer.android.com/privacy-and-security/keystore) and [OpenAI key safety](https://help.openai.com/en/articles/5112595-best-practices-for-api-key-safety)
